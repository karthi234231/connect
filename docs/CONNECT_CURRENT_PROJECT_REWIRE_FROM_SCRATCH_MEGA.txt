PURPOSE

Rebuild the application flow coherently from the request boundary to the UI and database so that every user-facing feature is genuinely functional, every mutation has a real backend path, every backend capability exposed by the current source is either wired into the UI or removed, and no production surface silently behaves like a demo.

PRODUCTION BAR
==============
Do not use the words “wired”, “complete”, “production-ready”, or “real” merely because a server action exists.
A feature is complete only when all of the following are true:
1. The user can reach it from a real route.
2. The UI calls exactly one canonical read/mutation boundary.
3. The boundary authenticates the caller independently of proxy/UI state.
4. Inputs are validated on the server.
5. Resource ownership / participant authorization is checked on the server.
6. Business invariants are enforced atomically where races are possible.
7. Database constraints/RLS protect the underlying records.
8. Success is persisted durably.
9. The UI refreshes or updates from server truth.
10. Failure is visible and distinguishable from an empty result.
11. Side effects are either transactional or placed behind durable outbox/work queues.
12. The flow has automated coverage for success, rejection, retry/race, and failure.

AUTHORITY RULES
===============
1. Proxy is NOT the sole authorization authority.
2. Every Server Action must authenticate and authorize itself.
3. Every API route must authenticate and authorize itself.
4. Services accept trusted actorId only from the action/API boundary, never from arbitrary client payloads.
5. RLS is the final data boundary.
6. Admin/service-role clients are used only in backend-only code for operations requiring elevated visibility; never returned directly to the browser.
7. Provider-owned profile identity fields cannot be written through user profile edit actions.
8. Public profile DTOs must be projections, not raw table rows.
9. A failure to verify a safety/security property must not silently convert into allow.

SECTION 1 — REQUEST GATE / PROXY
================================
CREATE FILE:
- proxy.ts

RESPONSIBILITIES
----------------
Proxy must do only coarse request concerns:
- identify session
- classify request as public / protected page / protected API / machine worker
- enforce safe redirect for browser navigation
- reject unauthenticated protected APIs with JSON 401
- redirect unauthenticated protected pages to /login?next=<safe-path>
- route suspended/deactivated users away from normal product routes
- enforce coarse rate limits
- attach request correlation id

NEVER put business resource authorization in proxy.
Examples that remain in service/action:
- can this organizer edit event X?
- can this user read thread Y?
- can this user review idea join request Z?

API RULE
--------
Protected API failures MUST NOT redirect to HTML login pages.
Return a machine-readable error envelope, e.g.:
{
  "error": {
    "code": "UNAUTHENTICATED",
    "message": "Authentication required.",
    "requestId": "..."
  }
}

PAGE RULE
---------
Protected page:
307 -> /login?next=<validated relative path>
Unsafe next values must be ignored.

SUSPENSION / DEACTIVATION
-------------------------
Do not query profiles on every request if it can be avoided without compromising policy; if proxy performs lifecycle checks, cache only safe-to-cache state with a short TTL and fail closed for high-risk paths.
Preferred robust pattern:
- proxy: coarse session presence
- layout/action/service: authoritative lifecycle check
- route handlers: authoritative lifecycle check

If proxy performs suspension reads, DB/read failure MUST NOT become “not suspended” automatically for privileged operations.
